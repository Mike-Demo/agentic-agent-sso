# Agent SSO for AgentID v0.1.0 — Full Code Review

## Verdict summary

The plugin has a solid OIDC baseline: authorization code with mandatory PKCE S256, browser-bound state, nonce validation, ES256-only signature verification, immutable-subject account matching, and fail-closed email collisions. However, the capability guard does not enforce the stated `manage_options` invariant in every case, the profile linking flow can be initiated cross-site without an intent nonce, and some OIDC claims are incompletely validated. There are also multisite cleanup, minimum-version, localization, and disclosure gaps. **Findings: 0 Critical, 1 High, 5 Medium, 7 Low, 0 Nit.**

## Findings

### High

1. **The capability ceiling does not guarantee that an agent can never hold `manage_options`.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-guards.php:133-150,177-188`. **What is wrong:** With an owner, the filter retains any agent capability also held by that owner, including `manage_options`. Without an owner, it removes only `manage_options` and leaves the rest of the agent's configured role capabilities untouched. Role demotion runs only on sign-in. **Why it matters:** An agent with an admin-capable role or direct capability grant can retain administrative capability when the owner also has it, and an unlinked agent is not capped at an owner's capabilities. This contradicts the stated “never admin” guarantee and may leave an existing session privileged until another sign-in. **Suggested fix:** Deny `manage_options` unconditionally in the capability filter for every agent, independently of owner capabilities and role demotion. Define and enforce a safe permission policy when no owner is linked; if the policy is an owner ceiling, do not grant owner-dependent capabilities until an owner is established.

### Medium

2. **The profile-link flow has no CSRF/intent nonce.** **Files:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-guards.php:228-237`; `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-auth.php:119-126,289-306`. **What is wrong:** The profile link is a GET URL to the public `agentid_login` handler. For `intent=link`, the handler checks only that the visitor is logged in; it does not verify a WordPress nonce before storing that user ID in the flow. The state cookie binds the OIDC response to the browser, but does not establish that the user intentionally began linking. **Why it matters:** A cross-site navigation can start the flow in a victim's browser. If the victim's AgentID session completes without a meaningful consent step, the callback can associate that agent subject with the victim's account. The flow does not sign the victim in as the agent, but it can create an unwanted or conflicting ownership link. **Suggested fix:** Require and verify a user-specific WordPress nonce when starting a link flow (or use a nonce-protected POST action), before recording `link_user_id`; retain the existing callback state and current-user checks.

3. **Multiple-audience ID tokens are accepted without validating `azp`.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-oidc.php:270-272`. **What is wrong:** The verifier accepts a token whenever the configured client ID appears anywhere in `aud`. It does not require or validate `azp` when `aud` contains multiple values. **Why it matters:** This omits OIDC validation for a multi-audience ID token and can accept a token whose authorized party is not this client. **Suggested fix:** When `aud` has multiple values, require `azp` and require it to equal the configured client ID; reject malformed audience and authorized-party claim types.

4. **Issued-at validation is optional and does not validate other temporal claims.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-oidc.php:274-279`. **What is wrong:** A missing or empty `iat` is accepted, and non-numeric values can be coerced to an integer. The verifier also does not reject a token whose `nbf` is in the future. **Why it matters:** A signed but malformed or not-yet-valid token can pass checks the code comments describe as validating ID-token timing. OIDC ID tokens require `iat`; JWT `nbf`, when present, is also a validity bound. **Suggested fix:** Require numeric `iat`, validate it against an explicitly documented clock-skew limit, and validate numeric `nbf` whenever present. Add tests for absent, malformed, and future temporal claims.

5. **Provisioning uses an agent email without requiring it to be verified.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-auth.php:382-390`. **What is wrong:** The code checks that `email` is syntactically valid, but does not require `email_verified` to be true before saving it as the WordPress account email. **Why it matters:** An unverified address can be stored as the agent's contact address and may receive site-generated mail or be consumed by other plugins as a verified identity attribute. Email collision checking prevents signing in as an existing account, but does not establish control of a new address. **Suggested fix:** Require a correctly typed, verified email before using it as the account email, or use a site-controlled placeholder and avoid presenting an unverified address as established identity data.

6. **Uninstall does not remove this plugin's per-site options on every multisite blog.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/uninstall.php:17-19`. **What is wrong:** `delete_option()` and `delete_transient()` operate on the current site. A multisite installation can have per-site `agentid_sso_options` (including a client secret) and caches on other blogs, which this uninstall handler does not visit. **Why it matters:** Uninstalling the plugin can leave credentials and cached issuer data in other site options tables. **Suggested fix:** On multisite uninstall, iterate the relevant site IDs with `switch_to_blog()` and remove the plugin's options and fixed transients on each site, then restore the original blog. Keep user-meta cleanup consistent with the chosen network-wide or per-site data policy.

### Low

7. **Untrusted claim shapes can reach string sanitizers without type checks.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-auth.php:365-368,382-384,459-460`. **What is wrong:** `email` and `owner_email` are passed to email sanitization without first confirming they are strings. A malformed array/object claim can trigger a PHP type error in the sign-in callback rather than a controlled authentication failure. **Why it matters:** A malformed provider response can turn a sign-in attempt into a fatal request; the same claim data is also consumed during metadata refresh. **Suggested fix:** Type-check each email claim before sanitization and fail closed or skip the optional owner-email field when its shape is invalid.

8. **The declared minimum WordPress version predates the block API version in use.** **Files:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/agent-sso-for-agentid.php:7`; `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/blocks/login-button/block.json:1`. **What is wrong:** The plugin declares WordPress 6.0 as its minimum while the block metadata declares API version 3, introduced in WordPress 6.3. **Why it matters:** The login-button block's editor behavior on the declared minimum version is not established and may be incompatible. **Suggested fix:** Test and support the block on WordPress 6.0 using a compatible API version, or raise the plugin minimum to the first supported version for API version 3.

9. **Admin-facing JavaScript strings are not localized.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/assets/js/admin.js:13-16,47-52`. **What is wrong:** “Copied,” “Copy,” and “Test failed.” are hard-coded English strings, unlike the PHP and block-editor strings that use the plugin text domain. **Why it matters:** These settings-page messages cannot be translated and fall short of the plugin's stated internationalization support. **Suggested fix:** Expose these strings through a WordPress i18n mechanism, such as `wp.i18n` with the plugin text domain or localized script data.

10. **The redirect-URI copy button reports success even when copying fails.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/assets/js/admin.js:10-16`. **What is wrong:** The code ignores the promise returned by `navigator.clipboard.writeText()` and changes the button to “Copied” even when the API is unavailable or the promise rejects. **Why it matters:** Administrators may believe they copied the redirect URI when they did not, delaying setup or causing a mismatched URI registration. **Suggested fix:** Show success only after the promise resolves, handle rejection and unsupported browsers, and provide a manual-copy fallback or clear failure message.

11. **The testing guide references a blueprint file that is absent from the repository.** **File:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/TESTING.md:19-20`. **What is wrong:** The guide says the Playground run used `tests/playground-blueprint.json`, but no such file is tracked or present in the repository. **Why it matters:** Readers cannot reproduce the documented Playground setup from the checked-in files, and the requested review scope's blueprint is missing. **Suggested fix:** Add the intended blueprint if it is available and permitted, or remove/update the reference and the related reproduction claims.

12. **The external-service disclosure overstates when the plugin contacts AgentID.** **Files:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/readme.txt:82-84`; `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/includes/class-agentid-settings.php:183-195`. **What is wrong:** The readme says service communication occurs “when — and only when a visitor starts” sign-in and “nothing is sent at any other time.” The administrator's “Test connection” action also fetches discovery and JWKS from AgentID. **Why it matters:** The external-service disclosure is not a complete description of the plugin's network behavior, even though the test sends no user identity token. **Suggested fix:** State that an administrator can trigger discovery/JWKS requests from the settings page, distinguish those requests from sign-in data, and describe the request metadata that the service necessarily receives.

13. **The external-service section does not link directly to the service's terms and privacy policy.** **Files:** `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/readme.txt:77-85`; `/home/runner/work/agent-sso-for-agentid/agent-sso-for-agentid/TESTING.md:52-53`. **What is wrong:** The readme points to the AgentID homepage and says to confirm the current terms and privacy policy there; the testing checklist also says those exact URLs remain to be confirmed. **Why it matters:** Users and plugin reviewers do not get direct links to the policies governing the external service, and the documentation itself identifies this as unfinished. **Suggested fix:** Confirm the current official terms and privacy URLs with AgentMail/AgentID and link those exact pages in the external-service disclosure.

## Per-dimension verdicts

1. **OIDC / authentication security — FAIL.** State, nonce, PKCE S256, single-use flow storage, issuer checking, ES256-only signature verification, and userinfo `sub` matching are implemented. The multi-audience `azp` and temporal-claim gaps are findings 3–4. No HS256 or `none` token is accepted by the explicit `ES256` check.
2. **Identity & account safety — FAIL.** Accounts are found by `sub`, email collisions fail closed, `actor_type=agent` is required in the signed ID token, and the explicit profile-link callback checks the current user. However, findings 1, 2, and 5 prevent certifying the `manage_options`, linking-intent, and verified-email guarantees. No direct code path was found that signs an agent in as an owner solely by email.
3. **Guards & session policy — FAIL.** Password authentication, resets, and application passwords are blocked for marked agent accounts; cookie expiration is capped to the configured 1–72 hours; deleted owners fall back to read-only capabilities and current owner capabilities are consulted dynamically. Finding 1 means the advertised capability ceiling is not guaranteed in all cases. The configured cookie-expiration filter does not by itself prove that already-issued sessions are shortened when settings change.
4. **WordPress platform correctness — FAIL.** Settings use the Settings API, the AJAX handler checks a nonce and capability, and displayed user-controlled values are escaped. Findings 6, 8, 9, 10, and 12 identify multisite, compatibility, localization, setup-feedback, and disclosure gaps. WooCommerce HPOS and checkout-block declarations exist, but actual runtime compatibility was not tested here.
5. **Code quality & standards — NOT VERIFIED.** PHP lint and the standalone JWT test passed in this review environment. `phpcs` is not installed here, so the claimed WordPress Coding Standards/PHPCompatibilityWP result could not be reproduced; PHP 7.4 runtime compatibility was also not exercised. Finding 7 describes a concrete malformed-claim error path.
6. **Docs ↔ code consistency — FAIL.** Findings 11–13 identify an absent referenced blueprint and inaccurate/incomplete external-service disclosures. The docs' claims of live discovery, real-app sign-in, and Playground behavior cannot all be established from the source alone; the full real-app and guard tests are explicitly unchecked in `TESTING.md`.
7. **WordPress.org readiness — NOT VERIFIED.** The readme has an external-services and privacy section, but finding 13 leaves direct policy links incomplete. `TESTING.md` says AgentMail permission for the AgentID name, a real-app flow, outside security review, and Plugin Check are still pending. Evidence needed: written trademark permission or approved naming, current policy URLs, a completed end-to-end test record, an independent security review, and a Plugin Check result.

## Top 5 risks

1. **Agent capability escalation:** `manage_options` can survive the owner-capability intersection, and unlinked agents are not capped at an owner's capabilities (finding 1).
2. **Unintended owner linking:** A cross-site request can initiate a link flow without a user-intent nonce (finding 2).
3. **Incomplete OIDC claim validation:** Multi-audience tokens do not validate `azp`, and missing/malformed time claims are accepted (findings 3–4).
4. **Unverified contact identity:** A syntactically valid but unverified agent email is stored as the WordPress account email (finding 5).
5. **Residual multisite credentials:** Uninstalling from a multisite can leave client secrets in other blogs' options tables (finding 6).
