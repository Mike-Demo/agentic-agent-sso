# Round-two response review: JIT provisioning

**Verdict: send with fixes.** The token-validation, subject matching, role-selection, password-reset, and `wp_login` claims have a sound basis in the code, but the proposed reply makes two material reassurances the implementation does not support: that the runtime protections last for the account's whole lifetime, and that every role without a listed hard-denied capability is non-privileged. Three real gaps a reviewer could reasonably treat as unresolved are role grants outside the hard-deny list (notably WooCommerce management), bypass of WordPress's `authenticate`/`wp_signon()` path, and the placeholder reconnect trust condition. Fix the wording, but do not present these as wording-only shortcomings; the code risks are real.

This is a source review of the checked-in v0.1.5 implementation. Line references below are repository-relative.

## B. Likely reviewer follow-ups

| A WooCommerce `shop_manager` or custom role can manage products/orders even though the plugin says agents cannot administer the site. | **Real gap** | `provisionable_roles()` only filters the 32 names above (`includes/class-agentid-settings.php:69-81`; `includes/class-agentid-guards.php:133-167`). WooCommerce is supported by the plugin, but its capabilities are not in the deny set (`agentkey-sign-in-agentid.php:5,109-121`). A `shop_manager` role, or custom role with commerce-management capabilities, can therefore pass the role test. With no owner recorded, those capabilities are not removed by the owner ceiling either (`includes/class-agentid-guards.php:190-205`). The reply cannot honestly say this set bars all site administration. |
| Author/publisher or custom roles can publish content or carry other powerful capabilities without any denied capability. | **Real scope gap; wording fix alone is insufficient** | `author` is an explicit fallback candidate (`includes/class-agentid-settings.php:94-101`), and custom roles are accepted if they avoid the deny list (`:69-81`). The runtime filter denies only the same set (plus the optional owner ceiling), not all publishing or plugin-defined capabilities (`includes/class-agentid-guards.php:179-207`). Do not portray “not in this blacklist” as “least privilege.” If the intended policy is no content publishing or no non-subscriber privileges, the code must enforce a narrower role/capability policy. |
| Open registration or a pre-existing account can collide with the synthetic placeholder email and be claimed by the agent. | **Real gap in the reconnect trust condition; exploitability depends on how the address was obtained** | The placeholder is a hash-derived email (`includes/class-agentid-auth.php:520-527`), but reconnect trusts an existing account when its email equals that value and `agentid_sub` is empty (`:480-502`). It does not require an independent retained-agent marker or check that the account was created by this plugin. An account pre-created by an administrator or registration flow that permits claiming the exact non-deliverable address can therefore be converted/reconnected; the code retains any role in the provisionable set (`:493-500`). The plugin does not enable core open registration, and an exact placeholder collision requires knowing/setting the subject-derived address, so do not imply this is automatically exploitable on every open-registration site. Still, the hash-derived address is not proof that the account was created for that agent. |
| What if the site uses core open registration? | **Partly answered; not a defense to the above** | This plugin does not set WordPress's open-registration option; provisioning is its own callback path (`includes/class-agentid-auth.php:511-585`). Core open registration alone does not demonstrate that a visitor can claim an arbitrary `.invalid` address, but custom registration flows or pre-created accounts may create the exact collision described above. Avoid arguing that an owner-configured IdP or core registration setting eliminates the trust-condition issue. |
| The plugin still implements its own login and bypasses security plugins' normal login checks. | **Real gap / directly responsive to the email** | The callback uses `wp_set_current_user()` and `wp_set_auth_cookie()` then invokes `wp_login` (`includes/class-agentid-auth.php:343-346`); it never calls `wp_signon()`/`wp_authenticate()` in that path. This preserves the action for observers but does not execute `authenticate` checks. A security plugin whose lockout, allow-list, MFA, or login policy is enforced only in that filter can be bypassed. Whether the team accepts an OIDC callback using core cookie APIs is a reviewer decision; do not claim these checks are honored. |
| Does `wp_insert_user()` at least let other plugins observe creation? | **Mostly answered, not a substitute for login checks** | The plugin calls core `wp_insert_user()` (`includes/class-agentid-auth.php:572-580`), so normal core user-creation hooks can observe creation. Creation hooks also do not compensate for the missing `authenticate` path when the new user is signed in. |
| Why not use an application password instead? | **Answered by a wording clarification** | Application passwords are credentials for an existing WP account/API client, not a way to validate a new federated AgentID identity. The plugin intentionally disables them on its marked agent accounts (`includes/class-agentid-guards.php:105-118`). Explain the distinction without dismissing application passwords for a human account's API use. |
| Are password/reset/application-password controls permanent, including deactivation and uninstall? | **Real lifetime limitation** | The guards are hooks registered at plugin init (`agentkey-sign-in-agentid.php:123-132`; `includes/class-agentid-guards.php:35-46`). | Does an “owner” always provide an additional least-privilege ceiling? | **Overstated** | The owner ceiling applies only when `agentid_owner_user_id` resolves to an existing user; with no owner, role capabilities remain except for the finite denies (`includes/class-agentid-guards.php:190-205`). ## C. Review of the proposed documentation

### Provisioning docblock

The draft's explanation that provisioning follows verified claims, requires `actor_type=agent`, keys the account to `sub`, and uses `safe_default_role()` is directionally accurate (`includes/class-agentid-auth.php:505-510,511-537,567-585`; `includes/class-agentid-oidc.php:227-327`). It is not accurate to state without qualification that the capability ceiling applies for the account's “whole lifetime” (`includes/class-agentid-guards.php:179-207`; `uninstall.php:45-59`). It should also say that “safe” means *no capability in this plugin's explicit 32-capability deny list*, not no possible administrative, publishing, or commerce-management capability. The special placeholder reconnect route is worth mentioning because a cold reader otherwise reads “matched by immutable sub, never by email” as having no exception (`includes/class-agentid-auth.php:480-502`).

### FAQ entry

The first sentence is a fair high-level description of this implementation, but “the same pattern other SSO plugins use” is broad and unnecessary. “Only ever receive roles that grant no site-administration capabilities” is inaccurate as an unqualified assurance: a role passes if it avoids the finite blacklist, even if it grants WooCommerce or content-publishing powers (`includes/class-agentid-settings.php:69-81`; `includes/class-agentid-guards.php:133-167`). The “whole lifetime” and unqualified password statement need an active-plugin qualifier. The FAQ should not be published unchanged; it should describe the precise policy, or be held until the policy gaps above are addressed.

Suggested safer replacement language for both drafts (not a code change):

> While this plugin is active, it provisions a local WordPress account after the AgentID ID token has passed signature and claim validation, including `actor_type=agent`. It finds established agent accounts by AgentID subject (`sub`). A verified-email collision is refused; after uninstall, a subject-derived placeholder account may be reconnected automatically. The configured role is accepted only if it avoids the plugin's explicit hard-deny capability list; otherwise the plugin selects its fallback role, or refuses new provisioning if no fallback is available. This list is not an exhaustive deny-list for every plugin's capabilities. The plugin also fires `wp_login`, but its callback does not run WordPress's `authenticate` filter chain. Account guards depend on this plugin being active.

This replacement is deliberately candid, not a substitute for fixing the real gaps if the intended promise is that agents cannot exercise any elevated capability or that all host login-policy filters are respected.

## D. Small, low-risk recommendations (suggestions only)

1. **Before replying, remove the whole-lifetime and comprehensive-role assurances.** If the actual product requirement is stronger than the finite list, treat it as a code issue, not a documentation issue.
2. **Revisit role policy.** The smallest straightforward risk reduction is to provision only `subscriber` (or another explicitly reviewed narrow allowlist) rather than accepting arbitrary custom roles and unlisted plugin capabilities. If keeping configurable roles, add a reviewed WooCommerce deny set and define what publishing/content capabilities are allowed.
3. **Make retained-account reconnect unambiguous.** Do not treat possession of a deterministic email alone as proof that an account was previously created for that subject. Safest low-complexity option is requiring admin reconnection after uninstall; alternatively preserve and verify a dedicated subject-bound marker that ordinary registration cannot manufacture.
4. **Clarify the custom-login compatibility story.** Ask the Plugins Team whether an OIDC callback that issues a core auth cookie and fires `wp_login` is acceptable despite not executing `authenticate` policies. If it is, document that integration boundary and test with representative security plugins; do not claim that `wp_login` makes the flow equivalent to `wp_signon()`.
5. **Qualify lifecycle claims.** State that runtime guards apply while the plugin is active. If protections are intended to persist through deactivation, design and test an explicit deactivation policy rather than relying on hooks in an inactive plugin.

## Suggested issue-summary comment
